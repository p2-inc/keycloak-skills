# benchmarks

Task definitions from [skillsbench](https://github.com/anthropics/skillsbench) used to evaluate the skills in [`plugins/`](../plugins/) against real sandboxed scenarios.

This directory is not part of the distributable plugin content — it's excluded from skillsaw linting (see [`.skillsaw.yaml`](../.skillsaw.yaml)) and isn't installed by `/plugin install`.

Each subdirectory is one benchmark task, copied from the skillsbench task tree (`environment/`, `oracle/`, `verifier/`, `task.md`). Per-run output (`jobs/`) is not copied here — it's execution history, not part of the task definition, and stays in the skillsbench working tree.

## Tasks

- [`keycloak-magic-link-login/`](keycloak-magic-link-login/) — provision magic-link passwordless login on a realm, correctly configuring outgoing mail and disabling silent account auto-creation. Exercises the `keycloak` skill's passwordless/magic-link guidance.
- [`keycloak-passwordless-passkey-login/`](keycloak-passwordless-passkey-login/) — provision passkey-only WebAuthn login (no password fallback), covering the WebAuthn passwordless policy, authoring/binding the flow, and the credential-bootstrap problem for zero-credential users. Exercises the `keycloak` skill's passwordless/passkey guidance (`admin:passwordless-passkey`).
- [`keycloak-corporate-sso-login/`](keycloak-corporate-sso-login/) — route a customer's staff to their own identity provider by email domain while internal staff keep password login. Exercises the `admin:corporate-sso` intent (MCP and REST variants).
- [`keycloak-org-restrict-login/`](keycloak-org-restrict-login/) — restrict *local password* login to members of one organization via `ext-select-org` in the browser flow, gated on `account_hint`. Exercises the `admin:org-restrict-login` intent (MCP and REST variants).
- [`keycloak-idp-org-restrict-login/`](keycloak-idp-org-restrict-login/) — gate a *federated* login on organization membership: broker a partner IdP, link it to an organization, and bind a post-broker flow containing `ext-select-org` so `account_hint` decides who gets in. Exercises the `admin:idp-org-restrict-login` intent (MCP and REST variants).
- [`keycloak-email-otp-login/`](keycloak-email-otp-login/) — passwordless login by an emailed 6-digit code (`ext-email-otp`), which unlike magic-link ships with no auto-created flow. Tests the non-obvious part: the identifier step must be an identifier-*only* authenticator, because stock `auth-username-form` rejects unknown addresses with "Invalid username or email" before `ext-email-otp` runs and leaks which addresses have accounts. Exercises the `admin:email-otp-login` intent (MCP and REST variants).
- [`keycloak-password-email-otp-mfa/`](keycloak-password-email-otp-mfa/) — the same `ext-email-otp` authenticator used as a *second factor* behind a still-required password. The decisive assertion is that a **wrong password sends no mail at all**: a flow that merely puts a code step in front of a login passes a happy-path test while leaving the password irrelevant. Exercises the `admin:password-email-otp-mfa` intent (MCP and REST variants).
- [`keycloak-magic-link-org-restrict-login/`](keycloak-magic-link-org-restrict-login/) — combine passwordless magic-link login with an organization-membership gate: a custom flow (`ext-auth-username-auth-note` → `ext-select-org` → `ext-magic-form`, in that load-bearing order) so the org check runs *before* any login email is sent — a non-member must receive no mail at all, not merely fail to complete login. Exercises the `admin:passwordless-magic-link-org-restrict` intent (MCP and REST variants), and specifically tests whether the router correctly detects this combined scenario rather than routing to plain magic-link or plain org-restrict alone.
- [`keycloak-social-login/`](keycloak-social-login/) — add a built-in "Sign in with GitHub" consumer social identity provider. Config-state-assertion only: Keycloak's built-in social providers point at hardcoded real vendor endpoints, so no live brokered login is attempted or possible in a `no-network` sandbox. The decisive assertion is that GitHub's actual claim shape (`login` for username, one `name` field, no `given_name`/`family_name`/`preferred_username` split) is mapped correctly, using GitHub's own compatible mapper type (`github-user-attribute-mapper`, not the generic `oidc-user-attribute-idp-mapper`) — a configuration that blindly copies an OIDC-standard mapping pattern from a Google/Auth0/generic-OIDC intent looks complete but silently maps nothing. Exercises the `admin:social-login` intent (MCP and REST variants).
- [`keycloak-zero-password-login/`](keycloak-zero-password-login/) — the "0 password required login flow": one browser flow offering a passkey **or** a magic link as alternatives, with no password authenticator anywhere. Drives both halves for real (magic link over plain HTTP; the passkey through a headless browser with a CDP virtual authenticator) and checks the create-user-if-none-exists trap, which in a zero-password flow is the whole authentication boundary. Exercises the `admin:zero-password-login` intent (MCP and REST variants).
- [`keycloak-idp-federation-login/`](keycloak-idp-federation-login/) — broker a partner company's own identity provider as a **plain login option**: a login button anyone can use, with no domain routing and no organization gate. A second realm in the same container stands in for the partner's IdP, so a real brokered OIDC login runs end to end. The decisive assertion is that **any** partner user completes login with no `account_hint` and no membership check — the check that separates this from the two org-restrict intents, whose recipes an agent may have just applied and can easily carry over by reflex. Also asserts the partner's claims land on the brokered Keycloak user (`email`/`firstName`/`lastName`) and that the partner realm is left untouched. Exercises the `admin:idp-federation` intent (MCP and REST variants).
- [`keycloak-credential-enrollment/`](keycloak-credential-enrollment/) — get a credential onto users who **already exist**: the step every passwordless intent leaves dangling, and the one place where the right mechanism is decided by a property of the *user* rather than by preference. Two staff differ deliberately — one already signs in with a password (reachable by a required action on her account, no mail involved), one has no credential at all (reachable only by an action-token email, which needs realm SMTP). The realm ships `CONFIGURE_TOTP` **registered but disabled**, so a pending required action is accepted by the API and silently never prompts; the decisive assertion drives a **real login** rather than reading config back, because those two states are indistinguishable from the outside. The other decisive assertion is negative: the credential-less user must still have **no password** at the end — setting him a temporary one satisfies a naive reading of the goal while defeating its point. Stock Keycloak throughout, no p2-inc extension jar. Exercises the `admin:credential-enrollment` intent (MCP and REST variants).
- [`keycloak-idp-initiated-sso/`](keycloak-idp-initiated-sso/) — wire **portal tiles** (an Okta dashboard tile, an Entra "My Apps" tile) so an unsolicited SAML response lands the user inside *one specific* client, for two already-federated SAML providers and two different target clients. Everything lives on the **client**, not the identity provider (`saml_idp_initiated_sso_url_name` and friends), which is not where the Okta/Entra-shaped request points. The decisive assertion is the **delivery shape for the OIDC target**: it must arrive as a 302 browser redirect to the app's main page, which means reaching Keycloak's REDIRECT branch past two attributes that silently outrank it (`saml_assertion_consumer_url_post`, `adminUrl`) and a `saml.force.post.binding` flag that silently overrides it — a configuration copied from the SAML recipe still "logs someone in" while auto-POSTing a SAML form at an app that cannot read one. Also pins that RelayState *cannot* route (it looks exactly like the mechanism and is discarded), and the broker-vs-direct client-protocol-check asymmetry that lets an OIDC app be a tile target at all. Vendors are mocked (unsigned assertions, signature validation deliberately off) because the sandbox is `no-network`. Exercises the `admin:idp-initiated-sso` intent (MCP and REST variants).
